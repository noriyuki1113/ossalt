# 移行摩擦

## 一言定義

あるツールから別のツールに切り替える際に発生するコスト・障壁・リスクの総称。データ移行・機能ギャップへの対応・チームへの習熟・運用ルールの再設計・インテグレーションの再構築など、**「移れる」ことと「移り切れる」ことの間のギャップ**を表す軸。

## なぜ重要か

OSS 代替を検討するユーザーの多くは、移行摩擦を過小評価して移行を開始し、途中で断念するか Notion に戻るケースが多い。ossalt でこの軸を明示することは、**非現実的な期待を防ぎ、移行成功率を上げる**ために重要。

移行摩擦が大きい主な理由：

1. **機能ギャップ**: 元のツールの機能が移行先にそのまま存在しない
2. **データ構造の違い**: 移行元と移行先でデータモデルが異なり、自動変換が困難
3. **チームの慣性**: 組織内に定着した運用ルール・テンプレート・ワークフローの再設計が必要
4. **インテグレーションの再構築**: 外部ツールとの連携を再接続する手間
5. **移行ツールの未成熟**: 公式・非公式の移行支援ツールの完成度

## この軸で差が出るツール群

### Notion → 各ツールへの移行摩擦レベル

| 移行先 | 摩擦レベル | 主な摩擦ポイント |
|---|---|---|
| **AppFlowy** | 低〜中 | DB機能ギャップ（リレーション・formula）、インテグレーション再構築 |
| **Outline** | 中 | DB機能・タスク管理の消失、情報アーキテクチャの再設計 |
| **AFFiNE** | 中〜高 | DB機能ギャップ、安定性への適応、セルフホスト設定 |
| **Anytype** | 高 | データモデルの根本的な違い（オブジェクト型への再設計）、チーム展開困難 |

### 移行摩擦の構成要素

**1. データ移行の摩擦**
- テキスト・画像：多くのツールで Markdown / HTML エクスポート経由で移行可能
- データベース：リレーション・formula・linked DB は移行先での再設計が必要になることが多い
- テンプレート：多くの場合、移行先で再作成が必要

**2. 機能ギャップへの対応摩擦**
- 移行先にない機能を「使わない」か「別ツールで補う」かの意思決定が必要
- 特に Notion の DB 機能への依存度が高いほど摩擦が増大

**3. チーム・組織の摩擦**
- 個人移行: 自分で決断できるため摩擦は小さい
- チーム移行: 全員の学習・合意・運用ルール変更が必要
- 全社移行: IT 部門・経営承認・トレーニング・移行期間の並行運用が必要

**4. 運用モデルの摩擦**
- SaaS から セルフホスト OSS への移行は、**ソフトウェアの乗り換えではなく、運用責任の移管**を意味する
- アップデート・バックアップ・障害対応・セキュリティパッチがチーム側の責任になる

## ossaltでの使い方

### 移行摩擦チェックリスト

ossalt の Notion 代替ページで、ユーザーに以下を事前確認させることで移行失敗を減らせる：

- [ ] **DB 依存度の確認**: Notion でリレーション・formula・rollup を使っているか
- [ ] **インテグレーション棚卸し**: どの外部サービスと連携しているか（GitHub / Slack / Google Drive 等）
- [ ] **テンプレート資産の確認**: 何個のテンプレートを業務で使っているか
- [ ] **利用者の範囲**: 個人 / 小チーム / 全社
- [ ] **セルフホストの可否**: 誰がサーバーを管理するか
- [ ] **移行期間の許容**: 並行運用できる期間はどのくらいか

### 摩擦レベルと推奨戦略

| 摩擦レベル | 推奨アプローチ |
|---|---|
| **低（ドキュメント中心・個人）** | そのまま移行。AppFlowy / AFFiNE が候補 |
| **中（DB あり・小チーム）** | PoC で DB 機能の代替を確認してから判断 |
| **高（DB 多用・組織全体）** | 段階移行（wiki 部分だけ先に Outline 等に移すなど）|
| **非常に高（全社展開・SaaS→セルフホスト）** | パイロットチームで 3 ヶ月運用してから判断 |

### 比較記事での使い方

各比較記事（notion-vs-xxx.md）の「移行摩擦」セクションで具体的な摩擦ポイントを列挙し、この decision-axis ページにリンクする。ユーザーが「なぜこれが摩擦になるのか」を理解できるよう、概念説明はここに集約する。
