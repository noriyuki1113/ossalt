# 運用負荷（Ops Burden）

## 一言定義

SaaS から OSS セルフホストに移行した後に発生する継続的な維持コスト。初期導入コストとは別に、長期にわたってチームが負う責任の総量。

## なぜ重要か

SaaS を使っている間は、インフラの維持・セキュリティパッチ・バックアップ・障害対応はすべてベンダーの責任だった。OSS セルフホストに移行した瞬間、これらがチームの責任になる。ライセンス費用の削減が目的でも、運用コスト（人件費・時間）が上回るケースがある。

ossalt では「料金を払わなくていい」ではなく「別のコストが発生する」という視点を必ず提示する。

運用負荷を構成するコスト：
- **バージョンアップ**: セキュリティパッチ・新機能への追従
- **バックアップ管理**: データ損失リスクの自己管理
- **SSL証明書の更新**: Let's Encrypt の自動更新設定など
- **監視・アラート**: ダウン検知・ディスク容量・メモリ
- **ユーザー管理**: アカウント作成・権限設定・退職者対応
- **障害対応**: ダウン時の原因調査・復旧

## この軸で差が出るツール群

**運用負荷が比較的小さい**
- **Vikunja**: 更新頻度が低く、SQLite バックアップは単一ファイルのコピーで済む
- **NocoDB**: アップデートは Docker イメージの pull のみ。データは既存 DB 側で管理

**運用負荷が中程度**
- **Mattermost / Outline / Penpot**: PostgreSQL + S3 のバックアップ設計が必要。月1〜2回の更新作業
- **Plane**: Celery ワーカーの監視が追加で必要

**運用負荷が高い**
- **Rocket.Chat**: MongoDB の管理・多数のプラグインの互換性管理
- **AppFlowy Cloud**: マイクロサービス構成で障害箇所の特定が難しい
- **GitLab CE**: 全部入りのため更新・バックアップの規模が大きい

## ossaltでの使い方

saas ページの「Core decision axes」→「Ops burden」セクションで、移行後のチームへの責任転移を明示する。具体的には：

1. 「月に何時間の運用工数がかかるか」を目安として示す
2. 「運用できる人がチームにいるか」という問いをユーザーに投げる
3. 段階的移行（まず SaaS の安い代替を試す）という選択肢も示す

この軸は saas ページで必ず触れるが、ツールページでは「セルフホスト難易度」として具体的な構成要件に落とし込む。
