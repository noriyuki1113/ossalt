# Slack vs Zulip

## 比較の文脈

「Slack の情報流失・メッセージが埋もれる問題を根本的に解決したい」または「非同期コミュニケーションを重視する分散チームで Slack から移行したい」という動機での比較。Zulip は Slack の代替というより、**チームコミュニケーションの設計思想を根本から変えるツール**として捉えるべき。[Source](https://zulip.com/)

## TL;DR（どちらを選ぶべきか・条件付きで）

| 選ぶべき状況 | 推奨 |
|---|---|
| 情報が埋もれない非同期コミュニケーションが必要 | **Zulip** |
| 分散・時差のあるグローバルチームで使う | **Zulip** |
| Apache 2.0 の完全 OSS が必要 | **Zulip** |
| 過去の会話を検索・参照しやすくしたい | **Zulip** |
| Slack に近い UX での移行を優先 | **Mattermost（他候補）** |
| リアルタイムチャット・雑談文化のチーム | **Slack** |
| 非エンジニアが多いチーム | **Slack** |

|---|---|---|

## 各軸での詳細比較

### メッセージ構造の根本的な違い

Slack はチャンネルに流れるメッセージを任意でスレッドにまとめる構造。Zulip はすべてのメッセージが「ストリーム（チャンネル）+ トピック（スレッド名）」の 2 階層を**必須**とする構造。これによりメッセージが自動的に話題別に整理される。

この差が意味するのは、**Zulip では「どのトピックに属するか」を考えながら投稿する習慣**が必要になること。Slack の「とりあえず #general に投げる」という使い方は Zulip では成立しない。文化変容を受け入れる意思が前提。

### 非同期コミュニケーションの強さ

Zulip のトピック構造は、時差のある分散チームで非常に有効。「昨日の議論を今朝確認する」場合、Slack ではスクロールして探すが、Zulip では未読のトピックを選んで読める。**会話が「どこまで読んだか」をトピック単位で管理できる**ため、情報の取りこぼしが減る。

### 学習コストと文化変容

Zulip への移行は技術的な移行より**チームの思考・習慣の変容**が本質的な課題になる。Slack に慣れたチームが Zulip に移ると、最初は「なぜトピックが必要なのか」という抵抗が出やすい。移行成功の鍵はトップダウンのコミットメントと十分な移行期間。

## 移行摩擦

Slack → Zulip の主な摩擦：

1. **概念モデルの変化**: 「チャンネル + スレッド（任意）」→「ストリーム + トピック（必須）」は、Slack → Mattermost よりもはるかに大きな変化。
2. **チーム全員の学習コスト**: 一人が慣れるより全員が新しい使い方を学ぶ必要があり、チーム移行の調整が大変。
3. **Slack App 連携の消失**: Slack 互換 API を持たないため、連携の再構築コストが大きい。
4. **雑談文化の消失リスク**: トピック必須の構造は雑談・インフォーマルなコミュニケーションには向かず、チームの文化が変わる可能性がある。

## 日本語圏での選択傾向

日本語圏では Zulip の認知度は低く、Slack 代替として検討されることは少ない。技術系コミュニティの一部で「非同期コミュニケーション改善」の文脈で紹介されるが、実際の業務導入報告はほぼ見当たらない。

グローバルでは Recurse Center・Akamai・Wikimedia などの技術組織で採用されており、オープンソースコミュニティでの利用も多い。

## 結論

Zulip は **「Slack が持つ本質的な問題（情報の流失・検索困難・非同期の弱さ）を根本から解決したい」** チームのための選択肢。単純な「コスト削減のための Slack 代替」ではなく、**コミュニケーション設計を変える意思のあるチーム**に向く。

**Zulip を選ぶべきかの最重要チェック**：チームリーダーが「コミュニケーション文化を変えること」にコミットできるか。答えが「No」なら Mattermost を選ぶべき。
